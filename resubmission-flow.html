Resubmission flow — end-to-end

Walk through what happens when a designer rejects a component, what the factory sees, what gets recorded, and how it bubbles up to the dashboard. Each step shows the screen + what changes under the hood.

Mental model

Component
The logical thing being made — e.g. "Main woven label". Has many sample areas.
Sample area
Fit Sample / Strike Off / Lab Dip inside a component. Each has its own clock. PPS is always order-level.
Attempt (submission)
One pass through the cycle for a sample area — v1, v2, v3. This is what we measure.
Rejection
Flipping a sample area to REJECTED closes its current attempt and opens v+1 at OUTSTANDING. Other areas on the same component are untouched.
Worked example: "Main woven label" has Fit Sample (v1 approved), Strike Off (v1 approved), Lab Dip (v1 rejected → v2 outstanding). The component isn't "in rework" as a whole — Lab Dip on Main woven label is.

Data model — what actually gets stored

components
id, name, type, factory_name, current_status, requested_date, approved_date, …
Unchanged — these are the "logical" component rows you already have.
sample_submissions (new)
id, order_id, component_id (nullable), sample_type [FIT | STRIKE | LAB | PPS], attempt_no, requested_at, submitted_at, resolved_at, outcome [APPROVED | REJECTED], reason, notes, photo_url, actioned_by_user_id
One row per (order × component × sample_type × attempt). component_id is null for order-level samples (PPS always, plus Fit/Strike/Lab on orders without components). Unique index on (order_id, component_id, sample_type, attempt_no).
Status lives on the current submission row
The existing FIT_SAMPLE_STATUS / STRIKE_OFF_STATUS / LAB_DIP_STATUS / PPS_STATUS fields become "the status of the latest open attempt for this area." Historical attempts' final outcomes are preserved on their submission rows.
Endpoints
POST /api/samples/{submission_id}/reject → closes current, opens next attempt
POST /api/samples/{submission_id}/approve → closes current as approved
GET /api/orders/{id}/submissions → timeline for one order
GET /api/resubmissions/overview → dashboard data

Open decisions before we build

  1. Reason taxonomy. I proposed: Colour / Placement / Stitch / Material / Spec / Print / Other. Keep, trim, or add?
  2. Photos. Required on rejection, or always optional? (Structured photo of the issue is hugely useful for the factory.)
  3. Factory email on rejection. On by default (via existing automation toggles), or silent?
  4. Does v2 reset the target date? You said yes (cycle time per attempt) — confirming.
  5. Can a factory mark "can't do it, please respec"? Or is reject only a designer action? (Today's spec: designer-only.)
  6. Stuck threshold. Flag at 3+ attempts? 2+? Or days-on-current-attempt based?
